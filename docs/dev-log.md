# Журнал разработки (ub-mode)

Формат: действие — причина.

## Шаг 1

1. Подключил репозиторий `kclazzy/dropshiptest`, клонировал — в нём был только README, переиспользовать было нечего.
2. Проверил окружение (g++ 13, CMake 3.28, SQLite 3.45, OpenSSL) — чтобы собирать и проверять код, а не писать вслепую.
3. Сначала `Domain.hpp` и форма данных (`Cents`, `Platform`, `TaskType`) — от них зависят все модули; имена, которые хранятся в БД, определены в одном месте.
4. Тесты PricingEngine написаны раньше кода; первая красная сборка упала не на «нет реализации», а на `std::expected` — в режиме C++20 libstdc++ его не даёт (нужен C++23). ТЗ требует C++20, поэтому добавил `core/Expected.hpp` вместо повышения стандарта.
5. Вторая красная сборка — ожидаемые `undefined reference`; после реализации 18/18 зелёных, предупреждений нет.
6. Проценты хранятся в bp, а не в double: расчёт цены целочисленный; переполнение — явная ошибка (`PricingError::Overflow`).
7. Миграция v1 — схема из ТЗ дословно; v2 — требования пользователя (редактирование, история, Ozon/Avito): валюта, переопределения, `price_history`, `audit_log`, `v_product_overview`. История и аудит пишутся **триггерами**, чтобы код не мог про них забыть, а «что показывать» определено в одном представлении.
8. Тесты БД (включая 8 воркеров × 200 задач) написаны до реализации; красная сборка — `undefined reference`.
9. Первый запуск тестов БД падал недетерминированно (SIGSEGV/OOM). Причина — не код БД, а `CHECK_EQ`: он связывал ссылку внутрь временного `ResultSet`. Исправил макрос (копирование значений), а не отдельный тест.
10. Прогнал набор под ASan+UBSan и TSan: 41/41, замечаний нет.
11. Добавил каркас `extension-mv3/` (manifest, package.json, tsconfig) — по ТЗ Шага 1; исходники расширения — Шаг 2.

## Не выполнено

- Инструменты `crapper`, `dryer`, `mutator` из ub-mode в окружении недоступны, поэтому CRAP-метрика, поиск дублирования и мутационное тестирование не запускались. Функции небольшие, с ветвлением в основном в `quote`, `claimNextTask`, `applyOne`.
- `manifest.json` ссылается на `service-worker.ts`, `content-script.ts` и `popup.html`, которых ещё нет (Шаг 2); `vite.config.ts` тоже появится с исходниками. Расширение сейчас не собирается.
- Сборка под MSVC/Windows и через vcpkg не проверялась (только GCC 13, Linux). Файл `vcpkg.json` пока содержит только `sqlite3`; остальные зависимости добавляются по мере появления модулей.

## Шаг 2 (ядро ИИ, мост, расширение)

1. Сначала общий слой: `Json.hpp`, `Sha256`, `HttpTransport` (интерфейс + libcurl) — сеть заменяется заглушкой в тестах.
2. `Listing` — единственное место с промптом и проверкой ответа ИИ; `OllamaClient` и `CloudClient` только переводят это в запросы своего провайдера.
3. Мост: токен в первом пакете (браузерный WebSocket не умеет заголовки) + проверка Origin, потому что любая веб-страница может постучаться на localhost.
4. Облако: пресеты провайдеров; ключи только из окружения/файла-секрета, чтобы `settings.json` можно было показывать. Адреса Yandex и Gemini сверены по документации, DeepSeek — нет (помечено в пресете).
5. Воркер ИИ: тесты первыми (красная сборка — `Result` неоднозначен между `db` и `ai`, поправил в тесте). Нашёл пробел в очереди: «неверный ключ» не имеет смысла повторять, поэтому `failTask(…, allowRetry=false)`.
6. Запускаемое ядро `dropship_core_app`; дымовой запуск: создаёт БД/токен/настройки, по SIGTERM выходит с кодом 0.
7. Расширение: esbuild вместо Vite (меньше движущихся частей); BridgeClient не зависит от `chrome.*`, поэтому проверен в Node.
8. **Сквозной тест (настоящее ядро ↔ BridgeClient) поймал три реальные ошибки**, которых юнит-тесты не видели: (а) путь моста `/ws` — расширение стучалось на `/`; (б) Node-овский `WebSocket` шлёт `Origin: null`, и ядро справедливо его отклоняет — для теста взята библиотека `ws`; (в) на чистой базе нет магазина, импорт падал «no active store» — теперь при первом запуске создаётся «Мой каталог» (`Platform::Local`).
9. Обновление: чистая логика (`Updater`: сравнение версий, разбор релиза, защита от подмены имени репозитория) покрыта тестами; установку делает скрипт запуска, а не само ядро — процесс не заменяет собственный файл. Проверено: `UPDATE_APPLY` → код выхода 75.
10. ASan+UBSan и TSan: 177/177 без замечаний. Расширение: 30 тестов, `tsc` чисто.

## Не выполнено / не проверено (Шаг 2)

- Docker-образ и compose не собирались (в среде нет работающего демона Docker) — проверьте на сервере.
- Windows/MSVC: `run.cmd`, `update.cmd`, сборка через vcpkg не запускались.
- Само расширение не загружалось в настоящий Chrome (нет браузера с расширениями в среде): проверены логика клиента, извлечение на jsdom и сборка, но не клик по popup. Это первое, что стоит проверить руками.
- Реальная генерация через Ollama и облачные API не выполнялась (нет моделей/ключей/доступа): проверены запросы и разбор ответов на заглушках.
- Цепочка обновления целиком (`git pull` → пересборка → перезапуск) не прогонялась: проверены только её части.
- `crapper`/`dryer`/`mutator` по-прежнему недоступны.
- ORDER_FULFILLMENT_RESULT отложен до модуля автовыкупа; редактирование/просмотр товаров пока через SQL (GUI — Шаг 6).

## Шаг 3 (мониторинг цен и остатков)

1. Разобрал Модуль 3 ТЗ на проверяемые части: разбор страницы → применение состояния → прокси/лимиты → воркер → сервис. Каждая часть — чистая функция или класс с заглушкой сети, поэтому тестируется без интернета.
2. `PageParser` зеркалит `extract.ts` расширения (JSON-LD → meta). Дублирование логики осознанное: расширение работает в браузере, ядро — без него. Парсер проверен на битом/обрезанном JSON-LD, глубокой вложенности, мусоре.
3. `StateApplier`: одна транзакция на карточку; хэш состояния использует ту же функцию `variantStateHash`, что и импорт. Решение для неоднозначных случаев: безымянная цена при нескольких сохранённых вариантах **не применяется** (не угадываем, чья она); варианты, пропавшие со страницы, обнуляются только если страница назвала хотя бы один вариант по SKU.
4. Очередь: добавил `deferTask` — отложить задачу без расхода попытки. Без него лимит домена «съедал» бы попытки и карточки уходили в `ERROR` просто за то, что поставщик вежливо притормозили.
5. Прокси: выдача одним `UPDATE … RETURNING` (два воркера не получат один прокси). Принципиальное решение: если прокси заданы, но все на отдыхе — **ждём, а не идём напрямую**, чтобы не раскрыть свой адрес.
6. Куки сессии уходят только на домен поставщика: редиректы ядро проходит вручную (до 3), на чужой хост куки не передаются, не-http(s) цель отклоняется. Схема прокси проверяется по списку.
7. Замкнул цикл с расширением: когда расширение передаёт свежую сессию домена, карточки `CAPTCHA_BLOCKED` этого домена (и поддоменов; шаблонные символы в домене экранируются) возвращаются в мониторинг.
8. Сквозной тест: настоящее ядро + локальный «поставщик» на Node: импорт по цене 100 → мониторинг увидел 120 → в `price_history` две записи. Первая версия теста упала на моей же неоднозначной SQL-колонке, а не на коде.
9. ASan+UBSan и TSan: 225/225 без замечаний (предупреждения TSan о `atomic_thread_fence` — из стандартной библиотеки, как и раньше).

## Не выполнено / не проверено (Шаг 3)

- `curl_multi` из ТЗ заменён пулом потоков с блокирующим libcurl: проще и надёжнее при сотнях–тысячах карточек в час. Если понадобятся десятки тысяч одновременных соединений — пересмотреть.
- `curl-impersonate` (подмена TLS-отпечатка) не подключён: нужна отдельная сборка библиотеки; пока при блокировке по отпечатку сработает путь «капча через расширение».
- `SOLVE_CAPTCHA_REQUEST` / `SCRAPE_DYNAMIC_PAGE` (команды ядра → расширению) не отправляются: сейчас при блокировке пользователь сам открывает сайт и нажимает «Передать сессию». Автоматизация — вместе с автовыкупом (Шаг 5).
- Страницы, чья цена рисуется только JavaScript, не поддерживаются.
- Новые цены/остатки пока **не отправляются на витрину** — это адаптеры магазинов (Шаг 4); флаг `is_in_stock` и розничная цена уже готовы для них.
- Правила цен и прокси задаются SQL-запросами (GUI — Шаг 6).
- SOCKS5-прокси проверены только на уровне выбора схемы; реальный прокси в среде недоступен (HTTP-прокси проверен тестовым сервером).
- `crapper`/`dryer`/`mutator` по-прежнему недоступны.

## Шаг 4 (адаптеры магазинов)

1. **Сначала проверил, что API реально позволяют.** Официальную документацию Avito открыть не удалось (сайт заблокирован для чтения), docs.ozon.ru — одностраничное приложение без текста. Подтверждено по вторичным источникам: Ozon — адрес, заголовки `Client-Id`/`Api-Key`, `POST /v2/products/stocks` (100 за запрос, 80 запросов/мин, остаток на склад — раз в 2 мин на товар), существование `/v1/product/import/prices`. Не подтверждено: тело запроса цен Ozon, вся спецификация Avito (токен, остатки, цена). Эти части написаны по памяти, помечены в коде и в руководстве; адаптеры проверены только на заглушках.
2. **Объём сужен честно:** вместо «всё из интерфейса» сделаны цены+остатки существующих карточек. Публикация нового товара требует категорий и атрибутов Ozon, заказы и трек-номера — часть автовыкупа (Шаг 5); эти методы возвращают `Unsupported` с понятным текстом.
3. Транспорт получил PUT и `Content-Type` (форма токена Avito).
4. `CredentialVault`: AES-256-GCM, свежий nonce, привязанный AAD; повреждённый `secret.key` — ошибка, а не тихая замена (иначе сохранённые ключи магазинов стали бы нечитаемыми без предупреждения).
5. Цены уходят в рубли с округлением вверх (не ниже рассчитанной); цена 0 («не рассчитана») не отправляется никогда — только остаток.
6. Идемпотентность: `published_hash`; запись об успехе условна по `state_hash` — если цена изменилась, пока шёл запрос, вариант остаётся неотправленным (есть тест на гонку).
7. **Сквозной тест поймал настоящую гонку.** Первая версия защиты от «долбёжки» отклонённых вариантов сравнивала секунды (`updated_at > published_at`); изменение в ту же секунду, что и предыдущая отправка, терялось — тест падал примерно в 1 запуске из 5. Заменил на `rejected_hash` (сравнение состояний, а не времени), добавил регрессионный тест; 25 запусков подряд — 0 падений.
8. CLI (`store-add`, `store-list`, `variants`, `link`): ключи только через stdin; ввод ID проверяется (SQL-инъекции в аргументах не проходят — запросы параметризованы).
9. Фактически разведены три ограничителя: лимитер домена поставщика (Шаг 3), `TokenBucketRateLimiter` магазина и `deferTask` — отложить без расхода попытки.
10. ASan+UBSan и TSan: 267/267 без замечаний.

## Не выполнено / не проверено (Шаг 4)

- **Адаптеры Ozon и Avito не проверены на живых API** — только на заглушках и локальном двойнике. Первое, что нужно сделать с реальным аккаунтом: один товар, `link`, смотреть `store-list`.
- Публикация новых карточек, заказы, трек-номера — не реализованы (Шаг 5).
- Shopify, WooCommerce, eBay, Wildberries, Яндекс Маркет — адаптеров нет (`store-add` для них отказывает).
- Окно для управления магазинами/привязкой — Шаг 6; пока CLI.
- Ключ шифрования лежит рядом с базой на том же диске: защищает от копирования одной базы, но не от доступа к папке данных целиком.

## Шаг 5 (заказы и выкуп)

1. **Что сделано:** приём заказов (`ingestOrder`, идемпотентно по `external_order_id`), повторная проверка по **текущим** ценам перед отправкой команды (поставщик мог подорожать), воркер `AUTO_ORDER`, приём результата (`applyFulfillment`) с защищёнными переходами статусов, трек (`applyTracking` + `TRACKING_SYNC`), опрос заказов площадок (`pollStoreOrders`), фоновый `OrderService`, RPC `ORDER_FULFILLMENT_RESULT` / `ORDER_TRACKING_UPDATE` / `LIST_ORDERS`, CLI, миграция v4, расширение: обработчик `EXECUTE_AUTO_ORDER` и список заказов в popup.
2. **Главное решение — деньги.** Покупку нельзя повторять, если неизвестно, началась ли она. Поэтому: до отправки — условный `UPDATE … WHERE status='NEW'` (двойной отправки нет); таймаут/обрыв после отправки → `MANUAL_REVIEW` без повторов; только явный отказ расширения возвращает заказ в `NEW` и ставит повтор; расширение не подключено → `deferTask` без расхода попытки. Запоздавший «failed» не откатывает уже выкупленный заказ.
3. **Отклонение от ТЗ:** вместо полностью автоматического выкупа — **ассистированный режим** (расширение открывает страницу, человек платит). Причины: автозаполнение форм произвольных магазинов нельзя проверить без живых аккаунтов, а ошибка стоит денег. Расширение отвечает ошибкой на `auto_pay: true`.
4. Данные адреса покупателя — только текст (`textContent`), ограничены 4 КБ и обязаны быть JSON-объектом; адрес не пишется в журнал.
5. ASan+UBSan и TSan: 296/296 без замечаний; расширение: 43 теста, включая сквозной (`e2e-orders`: ядро + мост + заказ → команда → результат → трек).

## Не выполнено / не проверено (Шаг 5)

- **Автозаполнение и автооплата** — не реализованы (осознанно).
- **`fetchNewOrders` и `submitTrackingNumber` у Ozon и Avito не реализованы** (`Unsupported`): заказы вносятся `order-add`, трек — вручную в кабинете (ядро ставит пометку). Эндпоинты и форматы нужно сверить с официальной документацией.
- Расширение по-прежнему не загружалось в настоящий Chrome; сквозные тесты используют клиент моста с теми же обработчиками.
- Несколько расширений/окон одновременно не поддерживаются (один активный клиент моста).
- Окно управления заказами в приложении — Шаг 6; пока popup и CLI.
