# Журнал разработки (Rust + Tauri v2)

Прежняя реализация на C++20 удалена по решению владельца (безопасность памяти); она остаётся в истории git (`5af626f`).

## Шаг 1 — основа

**Сделано:** Cargo workspace (`src-tauri`), миграция со схемой из ТЗ, пул SQLite (WAL, `synchronous=NORMAL`, `foreign_keys`, `busy_timeout=5s`), модели, очередь задач (`enqueue_task`, `dequeue_next_task` одним `UPDATE … RETURNING`, `complete_task`, `fail_task`, `defer_task`), `PricingEngine`, команда Tauri `price_breakdown` и React-калькулятор.

**Проверено:** 29 тестов (`cargo test`), включая перебор ~2000 комбинаций правил/цен с проверкой инвариантов и гонку 8 воркеров за 200 задач (15 запусков подряд без сбоев); `cargo clippy --all-targets` без замечаний; `npm run build` фронтенда; компиляция приложения Tauri.

**Решения и отклонения от ТЗ**
1. **Прибыль — цель, а не побочный результат.** Цена — наименьшая, при которой фактическая чистая прибыль (комиссии округляются вверх по отдельности) не ниже `max(маржа + фикс. наценка, min_profit_minor)`. Это то же, что формула ТЗ, но без потери 1–2 копеек из-за округления. `raised_to_min_profit` показывает, что цена поднята ради минимальной прибыли.
2. **`min_price`** — безубыточная цена (прибыль ≥ 0), «без ухода в минус». `old_price = retail / (1 − скидка)`.
3. **`rounding_minor`** — шаг округления вверх (1000 = до 10 ₽); 0 — без округления. Психологические окончания (…99) пока не поддерживаются.
4. `acquiring_and_tax_percent` в схеме один (эквайринг + налог вместе), `F_packaging` передаётся во входных данных, в таблице его нет.
5. **`rquest` не используется:** на crates.io это пустая заглушка `0.0.0` (проект переименован в `wreq`, версия 6.0 пока release candidate, тянет BoringSSL). Решение по клиенту с подменой TLS-отпечатка — на шаге мониторинга, после проверки сборки `wreq`.
6. Секреты (`encrypted_credentials`, `proxy_url`) помечены `#[serde(skip)]` и не попадают в интерфейс.
7. Ошибки: `AppError::to_user_friendly_ru()`; в команды Tauri уходит только русский текст.

**Не сделано в шаге 1 (по плану):** адаптеры площадок, ИИ, мост и расширение, мониторинг, заказы, трей, мастер запуска, шифрование ключей.

**Пожелание владельца (получено во время шага 1):** кроме Ollama добавить **облачные ИИ-решения с инструкциями** → шаг 2: интерфейс `ContentGenerator` с реализациями Ollama и облачных провайдеров (OpenAI-совместимые, Anthropic, Gemini, Yandex и др.), ключи только в зашифрованном хранилище, раздел инструкций «как получить ключ».

## Шаг 2 — ИИ и адаптеры магазинов

**Сделано:** `ai/` (Ollama и облако: OpenAI-совместимые — OpenAI, OpenRouter, Groq, Together, Mistral, DeepSeek, «другой сервис»; Anthropic; Gemini), проверка ответа модели (схема из ТЗ, заголовок Avito ≤ 50 символов, лимиты), подсказки под Ozon/Avito/Web, фильтр стоп-слов (aho-corasick), воркер `AI_REWRITE`; `security` (AES-256-GCM, `secret.key` 0600), `settings`, миграция 0002; `stores/` (`StoreAdapter`, Ozon, Avito, `add_store`, `build_adapter`, лимитер `governor`); очередь получила фильтр по типу задач. Инструкции: `docs/AI_PROVIDERS.md`, `docs/STORES.md`.

**Проверено:** 79 тестов, `clippy` без замечаний. Тестовый HTTP-сервер проверяет форму запросов всех четырёх форматов, классификацию ошибок, невозможность утечки ключа в сообщения и редиректы, пачки по 100, обновление токена Avito и один повтор при 401.

**Решения**
1. Облачные провайдеры сведены к 4 форматам обмена; «Другой сервис» покрывает всё OpenAI-совместимое (LM Studio, vLLM, Яндекс и т. п.).
2. Ключ ИИ шифруется и хранится отдельно от настроек; в `Debug` и ошибки не попадает; редиректы выключены, по голому http ключ уходит только на localhost.
3. Текст поставщика в подсказке помечен как данные (защита от prompt injection); стоп-слова проверяются и до, и после модели.
4. Сбой одного объявления Avito (`Rejected`) не роняет остальные; ошибки ключей/сети останавливают всю пачку.

**Не проверено / не сделано:** живые Ozon/Avito/облачные API (адреса и модели — по памяти, см. предупреждения в документах); получение заказов и трек-номеров; справочники категорий Ozon и автосопоставление атрибутов; ответы на сообщения Avito; Shopify/WooCommerce.


## Шаг 3 — каталог, импорт, мост, мониторинг, расширение

| Что | Зачем | Доказательство |
|---|---|---|
| `catalog::apply_variant_state` + миграция 0003 | одно место, где цена/остаток поставщика превращается в розницу, флаг наличия и историю | 5 тестов |
| `import` | граница данных: проверка при входе, канонический URL → SHA-256, повторный импорт обновляет, а не дублирует | 6 тестов |
| `bridge` (axum WS, JSON-RPC 2.0) | расширение ↔ ядро; loopback, Origin `chrome-extension://`, AUTH/PAIR за 10 с, код привязки одноразовый (2 мин, 5 попыток), в базе только SHA-256 токена | 9 тестов по настоящему WebSocket |
| `monitor` (parse, fetch, scheduler, worker) | JSON-LD без float, SSRF-защита (проверка IP + закрепление DNS + перепроверка редиректов), пауза на домен, пул прокси с экспоненциальной паузой; блокировка/сеть **не** обнуляют остаток | 27 тестов |
| `sync` | шлём в магазин только то, что отличается от `published_hash` и не отклонялось (`rejected_hash`); «Повторить отклонённые» | 4 теста |
| `services` | мост + ИИ-очередь + цикл мониторинга (30 с) + синхронизация; cookies поставщиков шифруются | 4 теста |
| Расширение | перенос с коммита 5af626f, привязка по коду вместо файла токена, тесты C++ e2e удалены | 39 тестов vitest + сквозная проверка: **настоящий клиент расширения ↔ настоящий Rust-мост** (привязка, повторный вход по токену, импорт, дубликат, ошибка валидации) |

Решения и ограничения:
- Монитор читает цены только из JSON-LD (`schema.org/Offer`). Сайты без разметки обновляются повторным импортом через расширение — это сказано пользователю в статусе «нужен повторный импорт».
- Синхронизация с Ozon/Avito работает для вариантов с заполненным `external_variant_id` (offer_id/item_id). Создание карточек на площадках (OZON_PUBLISH) **не реализовано**.
- Эндпоинты Ozon/Avito по-прежнему написаны по памяти и не проверены на живых API.
- Chrome с загруженным расширением в этой среде не запускался; проверен клиентский код расширения в Node против настоящего сервера.

## Шаг 4 — заказы и ассистированный выкуп

| Что | Зачем | Доказательство |
|---|---|---|
| `orders::transition` (чистая таблица переходов) | недопустимые переходы невозможны; повтор события безопасен; начатый выкуп нельзя отменить в приложении | 3 теста, включая перебор всех пар «статус × событие» |
| `ingest_orders` + `evaluate_order` | проверка при входе; наличие, количество, правило цены, прибыль ≥ минимума → READY_TO_BUY, иначе MANUAL_REVIEW с русской подсказкой | 4 теста |
| `process_next_handoff` | задача на выкуп — **одна попытка**; статус QUEUED_FOR_EXT фиксируется **до** уведомления; автоповторов нет, повтор только по `UserRetry` | 4 теста |
| `record_purchase_result` / `record_tracking` / `push_tracking` | результат от расширения идемпотентен (supplier_order_id не перезаписывается), трек валидируется, площадка без поддержки → подсказка «передайте вручную» | 3 теста |
| Мост: push ядро→расширение, `LIST_ORDERS`, `ORDER_FULFILLMENT_RESULT`, `ORDER_TRACKING_UPDATE` | форматы совпадают с уже существующим кодом расширения (`url`, `sku`, `address`, суммы в копейках) | 2 теста (push доходит только до авторизованных; ответы расширения игнорируются) + сквозной тест RPC |

Ограничения Шага 4 (честно):
- Режим только **ассистированный**: расширение открывает страницу поставщика, оплачивает человек. Автооплаты нет и не планируется по умолчанию.
- Заказы **не скачиваются** с Ozon/Avito (в адаптерах `fetch_new_orders` = «не поддерживается»); заказ попадает в систему через `ingest_orders` (в Шаге 5 — ручное добавление в интерфейсе).
- Передача трека в магазин зависит от адаптера: сейчас «не поддерживается» → пользователю показывается подсказка.

## Шаг 6 — заказы Ozon

- `OzonAdapter::fetch_new_orders` (`/v3/posting/fbs/list`, пагинация, строка на товар отправления) и `submit_tracking` (`/v2/fbs/posting/tracking-number/set`). Эндпоинты и поля **по памяти**, документацию открыть не удалось (apifox отдал ошибку) — сверить на живом кабинете.

- Тесты: 5 новых (Ozon ×3 с моковым сервером, опрос ×2); всего 163.
- По-прежнему не сделано: создание карточек (нужны словари категорий/атрибутов и живая документация), заказы Avito, Shopify/WooCommerce/eBay, тихое автообновление.

### Что ещё можно оптимизировать (не сделано — не узкие места при реальной нагрузке)
1. **Поиск по названию**: сейчас 5000 строк читаются и фильтруются в Rust. Решение — отдельная таблица FTS5 с нормализованным в нижний регистр названием (уже применено для категорий), тогда ~1 мс.
2. **Импорт**: ~16 запросов на товар (проход через поток sqlx на каждый). Для пакетного импорта — общая транзакция и многострочные `INSERT`; для ручного импорта из расширения не нужно.
3. **`recalculate_store`**: по два запроса на вариант. Можно считать цену в Rust и писать пачкой `UPDATE … FROM (VALUES …)`; ожидаемо 5 с → <1 с.
4. **Очередь**: завершённые задачи копятся навсегда — добавить ежесуточную чистку `COMPLETED` старше 7 дней (иначе индекс растёт).
5. **`list_products` с большим offset**: keyset-пагинация по `id` вместо `OFFSET` (25 мс на 9000 — пока не нужно).
6. **HTTP-клиент мониторинга** создаётся на каждый запрос (из-за привязки DNS к проверенному IP) — кэшировать клиент по (хост, IP) на 60 с; выигрыш — в TLS-рукопожатиях, измерить можно только на живой сети.
7. **N+1 в `apply_observed`/`has_suppliers`**: один запрос на товар с подзапросом вместо трёх — копейки, пока проверок ~5/с.
